# AI 导购整套结构与对话提及商品设计

## 问题

AI 导购右侧当前把 `OUTFIT_ADVICE` 的候选快照全部按 `outfitRole` 分组。`STRONG_MATCH` 的结构化推荐项带有 Java 解析的穿搭角色，可以正常进入上装、下装等分组；`WEAK_FALLBACK` 的候选快照虽然可能包含多件真实商品，但被 Java 拒绝强推荐归因后没有 `outfitRole`，前端会把它们全部过滤掉。

因此页面会同时出现“24 件候选”和五个“暂无真实匹配商品”，左侧可能已经提到具体商品，右侧却没有商品卡、商品信息或加购入口。现有前端测试只覆盖带角色的强匹配，没有覆盖“整套穿搭 + 弱匹配 + 对话提及真实候选商品”。

## 目标

- 右侧上方保留上装、下装、外搭、鞋履、配饰的整套穿搭结构。
- 右侧下方展示左侧回答明确提及、且能由 Java 追溯到当前候选池的真实商品卡。
- 商品卡提供图片、商品名、颜色、尺码、版型、价格、库存、详情、加购和购买。
- 清楚区分“AI 强推荐”和“对话提及”，不把证据不足的商品伪装成强推荐。
- 如果回答只有商品文字而没有可核验的 `spuId + skuId`，不做名称猜测，明确提示本轮文字建议未绑定真实商品。
- 修复推荐区域的深色背景与深色文字冲突，保证标题、角色、提示和商品卡可读。

## 非目标

- 不允许前端从自然语言商品名模糊匹配 SKU。
- 不允许 Python 或前端创建价格、库存、商品状态或交易事实。
- 不改变 `STRONG_MATCH`、`WEAK_FALLBACK`、`EMPTY`、`ERROR` 的状态含义。
- 不把弱匹配商品计入推荐归因、曝光、点击或加购归因指标。
- 不修改 Python `product_refs` 契约；本次新增字段只存在于 Java 面向前端的响应与 SSE 完成事件中。

## 方案选择

采用“强推荐项与对话提及项分离”的方案。

不采用前端解析回答文字的方案，因为同名商品、多 SKU、颜色和尺码会造成错配。不只依赖提示词强制 Python 输出完整证据，因为模型输出和证据核验仍可能失败，页面必须能安全表达弱匹配。

## 数据模型

### Python 到 Java

继续使用现有 `product_refs`。每个引用仍包含 Python 选择的 `spu_id`、`sku_id`、理由、排序分和可选匹配证据。共享 `java-python-chat` 字段清单不变。

### Java 推荐决策

Java 对每个 Python 商品引用进行两阶段判定：

1. **对话提及校验**：`spuId + skuId` 必须存在于本轮 Java 候选池、未重复且商品可购买。通过后生成 `mentionedItems`，只保留 Java 可以确认的标识和穿搭角色，不采信证据不足的推荐理由。
2. **强推荐校验**：在通过提及校验的基础上，匹配证据必须与 Java 的需求意图和商品事实一致。通过后同时进入 `recommendedItems`。

未知商品、错误 SKU、重复引用、下架、售罄或零库存商品不会进入 `mentionedItems`。证据缺失或矛盾但商品身份真实、可购买时，可以作为“对话提及商品”展示，但不能显示 AI 推荐徽标、排序分或推荐归因理由。

新增 Java 前端 DTO：

```text
mentionedItems[]
  spuId
  skuId
  outfitRole
```

同步响应使用 `mentionedItems`；SSE `done` 事件使用 `mentioned_items`。`recommendedItems` 和 `recommended_items` 保持不变。

### 推荐状态

- 候选池为空：`EMPTY`。
- 存在强推荐项：`STRONG_MATCH`。
- 候选池存在但没有强推荐项：`WEAK_FALLBACK`，即使存在 `mentionedItems` 也不升级状态。
- 快照读取失败：前端 `ERROR`。

## 前端数据流

1. SSE 或同步回退返回 `recommendedItems`、`mentionedItems`、`recommendationId` 和状态。
2. 前端通过 `recommendationId` 读取 Java 保存的候选快照，取得实时可展示商品事实。
3. 前端只用 `spuId + skuId` 将 `recommendedItems` 和 `mentionedItems` 关联到快照商品。
4. `outfitRole` 优先使用强推荐项的角色，其次使用对话提及项中由 Java 计算的角色。
5. 过期请求继续由现有请求序号保护，旧请求不得覆盖新一轮结果。

## 右侧页面结构

### 标题区

标题显示“为你策展的单品”，数量文案改成：

```text
已绑定 1 件 · 候选 24 件
```

“已绑定”表示右侧能够提供真实商品卡的提及商品数量；候选数量表示 Java 本轮候选快照规模。

### 整套搭配结构

上方保留五个角色：上装、下装、外搭、鞋履、配饰。

每个角色展示紧凑摘要，而不是重复完整商品卡：

- 有强推荐商品：商品名 + “AI 推荐”。
- 有对话提及商品但未达强匹配：商品名 + “对话提及”。
- 没有绑定商品：显示“暂无绑定商品，请参考左侧文字建议”。

角色摘要不直接执行交易，点击商品名可以定位到下方对应商品卡或进入详情。

### 本轮推荐单品

整套结构下方增加“本轮推荐单品”。按 Python 引用顺序展示去重后的 `mentionedItems` 对应商品卡。强推荐项天然也是对话提及项，因此只展示一次。

商品卡复用现有 `ProductCard`：

- 展示 Java 快照中的图片、名称、颜色、尺码、版型、价格和库存。
- `STRONG_MATCH` 且属于 `recommendedItems` 时显示 AI 推荐徽标、推荐理由和排序分。
- 仅属于 `mentionedItems` 时显示“对话提及”标签，不显示未经核验的理由和排序分。
- 加购和购买沿用现有确认流程，由 Java 再次核验价格及库存。
- 弱匹配商品不携带推荐归因元数据，也不记录推荐曝光、点击或加购归因事件。

如果 `mentionedItems` 为空，显示：

```text
本轮文字建议未绑定真实商品，暂不提供加购。你可以补充品类、预算或尺码后重新推荐。
```

前端不得退回到商品名模糊匹配。

### 非整套商品推荐

非 `OUTFIT_ADVICE` 请求同样使用“本轮推荐单品”商品卡列表，但不显示五角色结构。现有主卡、辅助卡的视觉层级可以保留，数据来源改为绑定的提及商品，而不是整个候选快照。

## 视觉设计

推荐区域迁移到与商城一致的浅色米白主题：

- 页面背景使用暖米白，内容卡使用接近白色的表面。
- 标题使用深森林绿，辅助文字使用高对比灰绿色。
- 状态提示使用浅色语义背景，不再出现深底深字。
- 角色摘要用浅棕边框区分，AI 推荐使用绿色标签，对话提及使用中性标签。
- 商品卡继续使用现有商城卡片风格，操作按钮保持清晰的加购与购买层级。
- 桌面保持左右工作台布局；窄屏时对话区、整套结构和商品列表按顺序变为单列。

## 错误与边界状态

- SSE 失败后同步回退仍返回相同的 `mentionedItems` 语义。
- 候选快照读取失败时清空本轮卡片，显示重试提示，不沿用上一轮结果。
- `mentionedItems` 指向快照中不存在的商品时忽略该项并记录测试失败，不生成残缺卡片。
- 商品图片加载失败时沿用现有占位处理。
- 加购或购买时库存变化由 Java 交易接口返回真实结果，前端不承诺快照库存。

## 测试与验收

### Java

- 无证据但候选池内且可购买的引用：状态为 `WEAK_FALLBACK`，`recommendedItems` 为空，`mentionedItems` 包含该 SKU。
- 有效证据引用：同时进入 `recommendedItems` 与 `mentionedItems`，状态为 `STRONG_MATCH`。
- 未知、重复、下架、售罄和零库存引用：不进入 `mentionedItems`。
- 同步接口和 SSE `done` 分别输出 camelCase 与 snake_case 字段。
- 推荐归因持久化仍只选择 `recommendedItems`。

### 前端

- SSE 解析器兼容 `mentioned_items` 和 `mentionedItems`。
- “整套穿搭 + 弱匹配 + 24 件快照 + 1 件提及商品”必须显示五角色结构、一个“对话提及”摘要、一个真实商品卡和加购按钮。
- `mentionedItems` 为空时显示未绑定提示，不显示商品卡和加购按钮。
- 强推荐商品显示 AI 徽标和理由；弱提及商品不显示强推荐归因。
- 点击弱提及商品的加购仍使用真实 `skuId`，但不附带推荐归因元数据。
- 新请求晚于旧请求完成时，旧请求不得覆盖当前商品卡。

### 跨服务与视觉

- 运行 Python 与 Java 共享契约测试，确认 Python 字段集合没有变化。
- 运行后端 assistant、推荐决策、候选快照测试。
- 运行前端 SSE、AI 购物页、商品卡和交易动作测试。
- 使用真实弱匹配场景验证左侧提到的商品与右侧卡片名称、SKU 一致。
- 验证桌面与窄屏布局、文字对比度、空状态、错误状态和加购确认流程。
